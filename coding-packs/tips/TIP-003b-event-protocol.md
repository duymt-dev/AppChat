### 2. Transaction-final collector and sequence
1. Introduce `withEventTransaction` around a tenant transaction, binding one collector to its actual transaction client and workspace for its lifetime. `writeOutbox(tx,...)` validates/stages immutable event values in this collector and returns staged count; it does not acquire sequence locks mid-domain work. Same transaction may stage multiple batches; preserve call/batch order for events within one aggregate. Reject use outside enrolled transaction in v2 (`EVENT_TRANSACTION_REQUIRED`), crossworkspace staging, calls after closure, and leaking a live collector across requests. No global mutable tenant context.
2. Outer wrapper runs callback including domain writes, action log, idempotency, effect receipts and undo CAS, then performs exactly one terminal flush before transaction commit. Flush resolves all aggregate keys first, locks/allocates per-aggregate counter rows in deterministic `(kind,id)` order, advances counters transactionally and inserts outbox+dispatch rows. After sequence locks no callback/domain SQL/network is allowed. Every counter rollback is atomic with event rollback; no Redis INCR, nontransactional Postgres sequence gap or timestamp/UUID ordering fiction.
3. Keep producer counter separate from dispatch head/claims. Dispatcher must never hold producer sequence locks during effects. Producers already hold domain locks before final allocation; cross-domain domain-lock order remains governed by existing domain contracts. Sorted final lock acquisition eliminates newly introduced sequence A→B/B→A cycles even when helper called writer multiple times. Existing deadlock/serialization retry only retries a fully rolled-back database attempt with stable operation identity; never rerun external prepare or unknown effects.
4. Enroll Executor final tenant transaction and UndoService, direct ingress/system/approval/KB/AI reply/platform-bridge transaction owners listed in manifest. For helpers receiving caller tx, reuse collector; do not wrap another Prisma transaction. Known019b future event producers are explicitly enrolled: run-events.ts writes safe run.step/run.done in the same tenant transaction as persisted status/step; run.store/runner delegate final tenant persistence to that enrolled boundary. usage-settlement/usage-receipts/usage-recovery use the wrapper for tenant receipt/counter+event finalization; credit-meter/wallet/usage-receipt keep platform debit authoritative with a durable tenant intent, not a tenant wrapper around a platform transaction. Native regression injects crash before/after both finalizations and proves no duplicate debit/event and no uncollected run event. Keep045b platform first/durable tenant intent, no distributed transaction. Existing `afterCommit` is not a substitute for outbox. After a confirmed commit, failure of markDirty logs a safe warning but cannot turn committed action into failed response; durable sweep recovers. No swallowed commit/serialization error.

Collector memory is bounded, clones validated payload, drops on abort/finally. ### 4. Ordered dispatch and receipt modes
1. Dispatcher reloads authoritative event/tenant and validates envelope/version/registry before effects. Only aggregate head may claim execution; event sequence greater than head returns deferred with safe wakeup metadata, lower than head only accepts durable terminal proof. Poison/unknown head blocks same aggregate visibly; unrelated entities continue at bounded concurrency8. Duplicate transports converge on the same receipt set.
2. Short claim transaction creates expected per-consumer receipts from immutable event registry_version. Dispatch head claim uses fencing token; no long transaction across consumers/provider work. Canonical lock order for claim, takeover, native effect and reconciliation is aggregate head → dispatch row → event receipt(s) sorted by consumer name → domain/privacy roots in existing canonical domain order → final producer sequence allocation. No path holds a receipt then requests its head. Before each native effect transaction, lock/validate head/fence then dispatch row then receipt; takeover cannot commit a new claim while old effect transaction holds that receipt lock. Commit receipt atomically with effect. After effect commit, dispatcher may crash; reconcile committed receipts and advance head once, without running effect again.
3. Contract modes: `projection` runs a supplied DB-only callback with receipt in one enrolled tenant transaction; `action` passes a private kernel admission/receipt port to ActionExecutor with current system action authority supplied later by003c; `handoff` persists durable downstream operation and receipt together, declaring accepted reference rather than completed external effect. Disposition values applied, no_effect(with typed current-state reason), handed_off, blocked_unknown and failed. A callback returning void is not proof. Projections cannot use API/provider network or mutate business state through a renamed projection.
4. Neutral action port binds event, consumer, allowed action ID, input digest, target aggregate, epoch and receipt claim, generated only inside trusted dispatcher. It is not serialized from HTTP/tool input.003c owns system authority, domain handlers and Executor wiring; this TIP does not grant Owner or blanket permission by source='system'. Conflicting input under same receipt fails409; same completed receipt returns original safe reference. Pending approval/operation is not action success.
5. CrossDB effect cannot use tenant receipt as atomic platform proof. Adapter uses045b authoritative platform operation and durable tenant handoff, with same stable effect identity; no second trial wallet on replay. A handoff may advance event head only after durable downstream acceptance, and downstream domain/delivery queue must enforce its own order/current-state contract. If later effect depends on remote completion, adapter declares completion-required and leaves head waiting until reconciled. Unknown remote result never becomes retriable merely because a lease expires.
6. Event completes/head advances in CAS transaction only after every expected consumer has applied/no_effect/handed_off under its declared semantics. Failure in one cannot silently discard it; already applied consumers stay done. Waiting itself is not success. Producer final flush never takes a head lock; lazy head bootstrap is dispatcher-only. Receipt/head transactions do not take producer sequence locks except terminal flush of new events, after domain/receipt work; no sequence lock held across network. Blocked/failure output excludes payload/customer text.
