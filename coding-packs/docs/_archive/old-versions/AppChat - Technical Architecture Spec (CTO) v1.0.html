01 — Goals & Principles

Mục tiêu kiến trúc & nguyên tắc thiết kế

AppChat là nền tảng SaaS B2B đa tenant, hợp nhất 19 kênh nhắn tin về một hộp thư, vận hành bởi con người + AI Agent, phục vụ doanh nghiệp dịch vụ (Spa, Nha khoa, Phòng khám, Giáo dục, Du lịch, Ô tô, BĐS, Tài chính…).

Yêu cầu phi chức năng định hình kiến trúc (Architecturally-significant)

Thuộc tínhMục tiêu & hệ quả kiến trúc
RealtimeTin nhắn ra/vào hiển thị < 1s. → cần message broker + WebSocket/SSE, không poll.
Multi-tenant1 user/đội nhóm có nhiều workspace; cô lập dữ liệu tuyệt đối. → tenant_id ở mọi bảng + Row-Level Security.
Đàn hồi theo tảiCao điểm (Flash Sale, giờ vàng) gấp 5–10×. → ingestion bất đồng bộ qua queue, stateless workers, auto-scale.
Khả dụng kênh19 kênh với rate-limit/webhook khác nhau. → Channel Gateway chuẩn hoá, retry/back-off, outbox pattern.
Đo lường AITính phí theo token; ngưỡng chi tiêu. → Token Metering service ghi nhận mọi lượt gọi LLM, hạn mức theo workspace.
Tuân thủISO/IEC 42001 (AI governance), nhật ký audit 1 năm, quyền xoá dữ liệu. → audit log bất biến, data retention policy.

7 nguyên tắc kiến trúc

  1. API-first & contract-driven — mọi tính năng phơi qua API có hợp đồng OpenAPI; UI là một consumer.
  2. Event-driven cho luồng tin nhắn — ingestion/outbound đi qua broker; xử lý đồng bộ chỉ cho truy vấn.
  3. Tenant isolation by default — không truy vấn nào thiếu tenant_id; RLS ở tầng DB.
  4. Modular monolith trước, tách service khi cần — khởi đầu 1 codebase module hoá rõ ranh giới; tách dịch vụ theo điểm nóng (Channel Gateway, AI Worker).
  5. Stateless services — trạng thái ở DB/cache/broker; service scale ngang tự do.
  6. Idempotency & outbox — gửi tin/đồng bộ kênh đảm bảo "đúng-một-lần hiệu dụng".
  7. Single source of truth cho số liệu — Reports đọc từ data mart, không tính trùng (khớp nguyên tắc "1 con số 1 nguồn").

05 — Service Decomposition

Phân rã dịch vụ (13 domain services)

Mỗi dịch vụ = một bounded context, sở hữu schema riêng (cùng cluster Postgres, tách schema), ánh xạ module nghiệp vụ trong SRS.

1 · Identity & Workspace
User, workspace (đa tenant), membership, RBAC, billing seat, phiên đăng nhập (Phone-OTP/Zalo/Social), chuyển workspace.
2 · Channel Gateway
Adapter 19 kênh: nhận webhook, chuẩn hoá payload, gửi outbound, quản OAuth/token, rate-limit per channel, retry/outbox.
3 · Conversation / Inbox
Hội thoại hợp nhất, message, assignment, lifecycle stage, tag (dùng chung), folder views, presence/typing/seen.
4 · Contact / CRM360
Khách hàng, hồ sơ 360°, nguồn/kênh/khu vực, merge & dedupe, pipeline stage, custom fields.
5 · Sales Docs
Báo giá → Hợp đồng → Đơn hàng, AppFlow nối luồng + cập nhật pipeline; sản phẩm/dịch vụ (catalog).
6 · Ticket / SLA
Ticket, danh mục, gán/chuyển tiếp/escalation, đồng hồ SLA, kanban, comment, AI tự xử lý.
7 · Calendar / Booking
Lịch hẹn (form kiểu Google), follow-up theo giai đoạn (cadence), nhắc tự động, conflict-check.
8 · Marketing / Broadcast
Chiến dịch ZNS/Email/ZBS/SMS, phân khúc, phê duyệt (Chờ/Đã/Từ chối), funnel, template.
9 · AI Agent & RAG
Cấu hình agent (persona/model/hành động/routing), Knowledge Base, vector retrieval, handoff theo độ tin cậy.
10 · Workflow Engine
Trigger → condition → action → wait → goal; bộ mẫu (gồm theo ngành); chạy bất đồng bộ, lịch sử thực thi.
11 · Loyalty
Hạng thành viên, tích/đổi điểm, quy đổi điểm↔tiền, voucher, cấu hình chương trình, tích điểm tự động từ đơn.
12 · Billing & Token Metering
Gói SaaS, add-on, mua thêm token (A/B/C), ngân sách token, ngưỡng tạm ngừng, hoá đơn/QR, đối soát.
13 · Reporting / BI
Data mart, 10 báo cáo (5 nhóm), xuất theo ngày/tổng, "1 con số 1 nguồn", drill-down.
↔
Giao tiếp giữa dịch vụ: đồng bộ qua REST nội bộ cho truy vấn; bất đồng bộ qua domain events trên broker cho side-effect (vd order.completed → Loyalty cộng điểm; quote.won → Sales Docs tạo hợp đồng; message.received → AI Agent). Không gọi DB của nhau trực tiếp.
06 — Data Model

Mô hình dữ liệu & ERD (cốt lõi)

Mọi bảng nghiệp vụ mang tenant_id (workspace_id); khoá ngoại trong cùng tenant; RLS ép lọc.

-- Core entities (rút gọn) workspace(id, name, plan, status, owner_user_id, created_at) user(id, name, email, phone, status) membership(user_id, workspace_id, role, seat_type) -- N–N: 1 user ↔ nhiều workspace channel_account(id, workspace_id, channel, oauth_ref, status) contact(id, workspace_id, name, phone, zalo, email, source, city, ward, lifecycle_stage, owner_id, tier, points) -- CRM360 + Loyalty conversation(id, workspace_id, contact_id, channel_account_id, status, assignee_id, ai_mode, last_msg_at) message(id, conversation_id, direction, sender, type, body, attachments, channel_msg_id UNIQUE, created_at) -- idempotency tag(id, workspace_id, name, color) · contact_tag · conversation_tag deal / quote / contract / order(…, contact_id, total, status) ticket(id, workspace_id, contact_id, category, priority, status, assignee_id, sla_due_at) appointment(id, workspace_id, contact_id, start, end, status, remind) followup(id, workspace_id, contact_id, stage, due, step, owner) campaign(id, workspace_id, channel, segment, status, approval) ai_agent(id, workspace_id, persona, model, actions, routing) kb_document(id, workspace_id, title, body, embedding vector) -- RAG workflow(id, workspace_id, name, nodes jsonb, status) workflow_run(id, workflow_id, trigger, status, log jsonb) token_usage(id, workspace_id, agent_id, model, tokens, cost, at) -- metering invoice(id, workspace_id, plan, amount, method, status, file_ref) audit_log(id, workspace_id, actor_id, action, target, at) -- bất biến, 1 năm

Quy ước

  • tenant_id = workspace_id ở mọi bảng nghiệp vụ.
  • channel_msg_id UNIQUE → chống trùng khi webhook gửi lại.
  • jsonb cho cấu trúc linh hoạt (workflow nodes, agent actions, custom fields).
  • vector (pgvector) cho RAG; index HNSW.
  • Soft-delete + retention; xoá cứng sau 30 ngày.

Phân vùng & hiệu năng

  • message partition theo tháng + theo workspace lớn.
  • Hot path đọc inbox: index (workspace_id, status, last_msg_at).
  • OLTP không chạy báo cáo nặng — ETL sang ClickHouse.
  • Outbox table cho gửi kênh & webhook ra (đảm bảo giao hàng).
07 — Multi-tenancy

Mô hình đa tenant (Workspace)

1 khách hàng có thể có nhiều workspace; 1 user/đội nhóm thuộc nhiều workspace; mua thêm workspace = mua thêm 1 tài khoản.

Shared DB, shared schema + RLS(Chọn) mọi bảng có workspace_id; PostgreSQL Row-Level Security ép policy workspace_id = current_setting('app.tenant'). Tối ưu chi phí, vận hành đơn giản, cô lập logic chặt.
Shared DB, schema/tenantCân nhắc cho workspace Enterprise lớn cần cô lập mạnh hơn.
DB/tenantChỉ cho khách On-premise/Enterprise đặc thù (lộ trình).

  • Workspace switcher ở Settings — chuyển nhanh; mỗi workspace có plan/seats/token-budget riêng.
  • Billing theo workspace — seat, add-on, token đo lường tách biệt từng workspace.

08 — Channel Gateway

Channel Gateway — kiến trúc 19 kênh

Lớp adapter chuẩn hoá mọi kênh về một mô hình hội thoại/tin nhắn nội bộ — cô lập sự khác biệt API/webhook/rate-limit.

// Adapter interface (mỗi kênh hiện thực) interface ChannelAdapter { verifyWebhook(req): boolean parseInbound(payload): NormalizedMessage[] // → schema chung sendOutbound(msg): {channel_msg_id} // idempotent refreshAuth(account): OAuthToken rateLimit: {rpm, burst} }
Khía cạnhGiải pháp
InboundWebhook Receiver xác thực chữ ký → enqueue → Inbound worker parse + lưu (idempotent theo channel_msg_id).
OutboundOutbox pattern: ghi ý định gửi vào DB → Outbound worker gửi + cập nhật trạng thái; retry/back-off; respect rate-limit per channel.
AuthOAuth token store mã hoá; auto-refresh; cảnh báo khi token hết hạn (trạng thái kênh "error").
Khác biệt kênhTemplate ZNS duyệt trước; cửa sổ 24h của Messenger/WhatsApp; giới hạn đính kèm — gói trong adapter.
Mở rộngKênh tuỳ chỉnh qua webhook chuẩn → thêm kênh không cần đổi core.
09 — Realtime & Events

Realtime & kiến trúc hướng sự kiện

Realtime (WebSocket)

  • Socket Gateway theo workspace room + conversation room.
  • Đẩy: tin nhắn mới, typing, seen, assignment, presence.
  • Presence/typing qua Redis pub/sub; scale gateway bằng adapter Redis.
  • SSE fallback cho mạng hạn chế.

Domain events (broker)

message.received · message.sent conversation.assigned contact.created · contact.merged quote.won · order.completed ticket.sla_breach_risk campaign.approved ai.token_used workflow.triggered
◆
Ví dụ phản ứng chuỗi: order.completed → Loyalty cộng điểm (1.000đ=1 điểm) + Reporting cập nhật data mart + Workflow "chăm sóc sau dịch vụ" kích hoạt. Mỗi consumer độc lập, idempotent theo event id.

11 — API Design

Thiết kế API (REST · Webhook · WebSocket)

Nguyên tắc

  • REST tài nguyên, versioned /v1; phân trang cursor; lọc/sort chuẩn hoá.
  • Mọi request mang Authorization: Bearer + X-Workspace-Id.
  • Idempotency-Key cho POST gửi tin/tạo đơn.
  • Webhook ra (outbound) cho tích hợp ngoài; ký HMAC; retry có back-off.
  • Hợp đồng OpenAPI 3.1 là nguồn chân lý — sinh client & mock.
# REST (trích) GET /v1/conversations?status=open&cursor=… POST /v1/conversations/{id}/messages # gửi tin (Idempotency-Key) GET /v1/contacts/{id} # hồ sơ 360° POST /v1/quotes/{id}/win # Báo giá → Hợp đồng POST /v1/orders/{id}/complete # → cộng điểm Loyalty POST /v1/campaigns/{id}/approve GET /v1/reports/executive?from=…&to=… # xuất theo ngày # Webhook IN (kênh) / OUT (tích hợp) POST /webhooks/channels/{provider} # inbound, verify chữ ký POST {customer_url} event=order.completed # outbound, HMAC # WebSocket ws /realtime → subscribe(workspace, conversation) events: message.new · typing · seen · assigned

13 — Infrastructure

Hạ tầng, mở rộng & triển khai

Triển khai

  • Kubernetes; mỗi service/worker là Deployment riêng.
  • IaC bằng Terraform; cấu hình bằng Helm.
  • Môi trường: dev → staging → prod tách biệt hoàn toàn.
  • CI/CD: build → test → scan → blue/green / canary.

Mở rộng (scale)

  • Workers stateless auto-scale theo độ sâu hàng đợi.
  • Postgres: read replica cho truy vấn nặng; PgBouncer.
